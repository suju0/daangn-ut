# 당근 앱 리디자인 — UT Prototype 진행 페이지

개선 전(AS-IS) / 개선 후(TO-BE) 프로토타입을 차례로 써 보게 하고, 작업마다 설문을 받는
사용성 테스트 진행 화면입니다. 레이아웃은 Maze 를 참고했고, 색·간격·타이포·컴포넌트는
당근 SEED Design System 토큰(Rootage)을 그대로 옮겨 썼습니다.

---

## 실행

프로젝트 폴더의 **`UT 서버 켜기.cmd`** 를 더블클릭하세요.
검은 창이 뜨면서 서버가 켜지고 브라우저가 함께 열립니다.

터미널을 쓰신다면 같은 일을 하는 명령입니다.

```bash
node .claude/ut-server.js
```

- 진행 화면 — <http://localhost:8780/>
- 결과만 따로 — <http://localhost:8780/#/result>

> **서버는 프로그램이지 설치된 서비스가 아닙니다.** 검은 창을 닫거나 PC 를 껐다 켜면 꺼집니다.
> 꺼진 상태에서 주소를 열면 "연결할 수 없음" 이 뜨는데, 고장난 게 아니라 켜져 있지 않은 것입니다.
> 그때 `UT 서버 켜기.cmd` 를 다시 더블클릭하면 됩니다.
> **수집된 응답은 `ut/data/responses.json` 파일에 남아 있어서, 서버를 껐다 켜도 그대로입니다.**

> 서버는 **8780 하나**입니다. 진행 화면 · 결과 대시보드 · 응답 수집 API 가 모두 여기에 있습니다.
> 예전에 따로 쓰던 정적 서버(`root-server.js`)는 이 서버가 같은 일을 하므로 없앴습니다.
> 루트의 기존 페이지들(`daangn-my-analysis.html` 등)도 `http://localhost:8780/<파일명>` 으로 그대로 열립니다.

대시보드는 **진행 화면 안에서도** 볼 수 있습니다.
진행 화면 상단에 `진행 | 결과` 전환이 항상 있고, 결과를 누르면 같은 페이지에서 대시보드가 열립니다.
설문 진행 상태와 프로토타입 로딩은 그대로 남아 있어서, 다시 진행으로 돌아가면 보던 문항에서 이어집니다.

결과를 눌러도 **비밀번호를 통과해야 응답이 보입니다.** 참가자가 눌러도 남의 응답은 노출되지 않습니다.
별도 주소(`#/result`)도 그대로 살아 있어, 진행 화면 없이 결과만 따로 열 수도 있습니다.

대시보드 비밀번호는 **`daangn-ut-2026`** 입니다.
`js/config.js` 의 `OPTIONS.resultPasscodeHash` 에 SHA-256 해시만 저장되어 있고, 원문은 코드에 없습니다.
바꾸려면 새 비밀번호의 해시를 넣고 **서버를 다시 띄우면** 됩니다(서버가 이 값을 읽어 씁니다).

```bash
node -e "console.log(require('crypto').createHash('sha256').update('새비밀번호').digest('hex'))"
```

## 응답은 어떻게 쌓이나

참가자가 마지막 문항을 넘기면 **곧바로 서버로 전송되어 대시보드에 쌓입니다.**
파일을 저장해 전달하는 과정이 없습니다.

```
참가자 브라우저 ──POST /api/responses──▶ ut/data/responses.json ──▶ 대시보드
```

- 저장 위치: `ut/data/responses.json` (진행자 PC)
- 여러 참가자가 같은 서버에 붙어 각자 기기에서 진행해도 한곳에 모입니다
  (같은 네트워크라면 `http://<진행자 PC IP>:8780/` 으로 접속)
- 서버가 꺼져 있으면 브라우저에 남겨 두었다가, 서버가 켜진 뒤 대시보드를 열면 자동으로 올립니다.

### "응답 수집 서버에 연결하지 못했습니다" 가 뜬다면

거의 항상 **서버가 꺼져 있거나 주소가 틀린 경우**입니다.

- `UT 서버 켜기.cmd` 를 실행하지 않은 경우 → 서버가 없으니 저장되지 않습니다
- `ut/index.html` 파일을 더블클릭해서 연 경우 (`file://`) → 안 됩니다
- `http://localhost:8780/` 이 아닌 다른 주소로 연 경우 → 안 됩니다

서버 상태는 **세션을 시작하기 전에** 참가자 화면 상단에서 확인할 수 있습니다.
꺼져 있으면 진행률 왼쪽에 빨간 `응답 수집 서버 꺼짐` 배지가 뜹니다.
배지가 없으면 정상입니다. 끝나고 나서야 알게 되는 일이 없도록 미리 확인하고 시작하세요.

### 데이터 초기화

대시보드 오른쪽 위 **`데이터 초기화`** 버튼을 누르면 서버에 쌓인 응답과 이 브라우저에 남은 응답
(진행 중이던 임시 응답 포함)을 한 번에 지웁니다. 되돌릴 수 없으니 필요하면 먼저 CSV/JSON 을 받아 두세요.

> **응답은 이 버튼으로만 지웁니다.** 저장된 응답은 참가자를 다시 불러야만 복구되는 데이터입니다.
> 테스트로 만들어진 것처럼 보이는 응답이 있어도 임의로 지우지 않고, 어느 것이 그렇게 보이는지
> 알려 드린 뒤 판단을 기다립니다.

### 열람 제한

- `GET /api/responses` 는 진행자 비밀번호 헤더가 있어야 응답합니다. 참가자는 **제출만** 되고 **열람은 안 됩니다**.
- `ut/data/` 는 정적 경로로도 내주지 않습니다(403). 주소를 알아도 파일을 열 수 없습니다.
- 대시보드 링크는 참가자 화면 어디에도 없습니다.

다만 진행자 PC 에 파일로 있는 만큼, **그 PC 에 접근할 수 있는 사람은 볼 수 있습니다.**
비밀번호도 HTTPS 가 아닌 로컬 평문으로 오갑니다. 사내망 밖으로 열어 두지 마세요.

## 프로토타입 두 벌

개선 전 / 개선 후가 각각 **별도의 Figma 파일**로 연결되어 있습니다.

| 구간 | Figma 파일 | 시작 프레임 |
|---|---|---|
| 개선 전 (AS-IS) | `Daangn_UT_Prototype (AS-IS)` — `3xP3ycyRn2TdIZkkVlfjL5` | `11:3765` 나의 당근 탭 |
| 개선 후 (TO-BE) | `Daangn_UT_Prototype (TO-BE)` — `z1kIxzbitDMsJrsSh9bPFX` | `11:3765` 나의 당근 탭 |

두 파일 모두 383×801 래퍼 프레임(그림자 포함)이라 기기 영역 비율을 공유합니다.

바꾸려면 `js/config.js` 위쪽의 `PROTO_ASIS` / `PROTO_TOBE` 만 고치면 됩니다.
Figma 공유 > 프로토타입 링크가
`https://www.figma.com/proto/<fileKey>/<fileName>?node-id=<nodeId>` 형태이므로 세 값을 그대로 옮기면 됩니다.

```js
const PROTO_ASIS = figmaProto({
  fileKey: '3xP3ycyRn2TdIZkkVlfjL5',
  fileName: 'Daangn_UT_Prototype--AS-IS-',
  nodeId: '11-3765',
  startNodeId: '11:3765',
});
```

### Figma 를 고치면 테스트 화면에도 바로 반영됩니다

이 페이지는 Figma 프로토타입을 **iframe 으로 그대로 임베드**합니다. 화면을 코드로 다시 그린 게 아닙니다.
그래서 Figma 에서 디자인이나 프로토타입 연결을 고치면, 테스트 화면을 새로 고치는 순간 반영됩니다.
코드를 건드릴 필요가 없습니다.

바꿔 말하면 **Figma 가 유일한 기준**이고, 이 저장소에는 프로토타입 화면의 사본이 없습니다.

## 프로토타입 로딩

Figma 임베드는 첫 로드에 5~7초가 걸립니다. 이 시간을 없앨 수는 없으므로,
**참가자가 보지 않는 시간대로 전부 옮겨 두는 것**이 전략입니다.
로딩 화면을 보게 되는 건 페이지를 처음 열었을 때 한 번뿐입니다.

1. 페이지가 열리는 순간 **개선 전/후 두 벌을 동시에 미리 로드**합니다. 참가자가 안내와 참가자 정보 문항을
   읽는 동안 로딩이 끝나므로, 첫 작업은 기다림 없이 시작됩니다.
2. 지금 보여 주지 않는 쪽은 **숨기지 않고 화면 밖으로 밀어 둡니다.**
   `display:none` 으로 감추면 브라우저가 iframe 그리기를 미뤄서, Figma 앱이 실제로는 켜지지 않은 채
   대기하다가 화면에 나타나는 순간부터 로딩이 시작됩니다. 화면 밖에 두면 보이지만 않을 뿐 정상적으로 켜집니다.
   덕분에 **개선 전 → 개선 후로 넘어갈 때 로딩이 없습니다.**
3. **작업이 끝나도 프로토타입을 다시 부르지 않습니다.**
   예전에는 다음 작업을 위해 작업마다 첫 화면으로 되돌렸는데, 되돌리기는 결국 다시 불러오는 일이라
   미리 켜 둔 예비 프레임이 준비되기 전에 참가자가 빨리 넘어가면 그 로딩이 그대로 보였습니다
   (작업 2 → 작업 3 구간에서 실제로 확인). 지금은 한 구간 안에서는 화면을 계속 이어서 씁니다.
   그래서 **작업 2·3 은 참가자가 작업 1 을 끝낸 화면에서 이어서 시작합니다.**
   진행자가 첫 화면에서 시작하게 하고 싶으면 아래 **'처음 화면으로'** 를 누르면 됩니다.
   이때를 위해 첫 화면 상태로 미리 켜 둔 **예비 프레임을 한 장** 들고 있어서, 눌러도 기다림이 없습니다.
   예비 쪽은 투명·클릭 불가로 뒤에 겹쳐 둡니다.
   예비는 **한 번에 한 쪽만** 가집니다. Figma 임베드를 한 화면에 네 장 띄우면 그중 일부가
   검은 화면으로 남는 것을 확인했기 때문입니다(세 장까지는 정상. 브라우저의 WebGL 컨텍스트 수 제한으로 보입니다).
   그래서 본 프레임 두 장 + 예비 한 장, **최대 세 장**을 넘지 않게 유지하고,
   개선 전 → 개선 후로 넘어가면 예비도 함께 옮겨 갑니다.
4. 그래도 준비가 안 끝났다면 "화면을 준비하고 있어요"를 보여 주고, **준비된 뒤에 타이머를 시작합니다.**
5. 작업 도중에 프로토타입을 다시 불러오게 되면(예: '처음 화면으로'를 눌렀는데 예비 프레임이 아직
   준비되기 전이라면) **그동안 타이머를 멈춥니다.** 시계가 흐려지고 "화면을 다시 불러오는 중이에요.
   이 시간은 기록되지 않습니다."가 뜹니다. 로딩이 끝나면 멈춘 지점부터 이어서 흐릅니다.
   저장되는 `durationMs` 에는 멈춰 있던 시간이 빠져 있고, 얼마나 멈췄는지는
   `loadingPausedMs` 에 따로 남습니다. **로딩 시간은 어떤 경우에도 소요시간에 섞이지 않습니다.**
6. **프로토타입은 어느 화면에서든 그대로 눌러 볼 수 있습니다.** 잠그지 않습니다.
   Figma 안의 인터랙션이 그대로 살아 있어야 참가자가 실제 앱처럼 만져 볼 수 있기 때문입니다.
   프로토타입을 다시 불러오는 시점은 (1) 페이지를 처음 열 때 (2) 새 참가자를 시작할 때
   (3) 화면 아래 **'처음 화면으로'** 버튼을 누를 때, 이 세 가지뿐입니다.
   작업과 작업 사이에는 다시 부르지 않으므로, 구간 중간에 로딩이 보일 일이 없습니다.

### 기기 테두리

**프로토타입은 기기 상자 크기 그대로 보여 줍니다.** 확대하지도, 잘라내지도 않습니다.
개선 전/개선 후 모두 같은 `.device` 규칙을 쓰므로 크기가 항상 같습니다.

기기 상자에는 **배경색을 두지 않습니다(투명).** 예전에는 검정 배경을 깔아 두어서,
임베드가 상자보다 1~2px 작게 그려질 때 그 틈으로 검은 실선이 비쳤습니다. 지금은 틈이 생겨도
뒤에 있는 스테이지 배경(옅은 회색)이 비칠 뿐이라 눈에 띄지 않습니다.

모서리 반지름은 `css/ut.css` 의 `.device` 안 `--proto-corner` 한 곳에서 정합니다.
383×801 디자인 기준 px 값이고(지금 `50`), 비율로 환산해 쓰므로 화면 크기가 달라져도 유지됩니다.
코너에 선이 보이면 이 숫자만 조금 올리면 됩니다 — 프로토타입 크기는 바뀌지 않고 자르는 곡률만 달라집니다.

## Figma 프로토타입은 건드리지 않습니다

이 페이지는 Figma 파일을 **읽기만 합니다.** 프로토타입 공유 주소를 그대로 iframe 으로 띄우는 방식이라
파일에 쓰기를 할 수 있는 경로 자체가 없습니다. 연결·오버레이·스마트 애니메이트·딜레이 같은
프로토타입 설정은 전부 Figma 원본 그대로 동작하고, Figma 에서 고치면 새로고침 시 바로 반영됩니다.

다만 임베드 주소에 붙는 **표시 옵션**은 '누를 때의 느낌'을 바꿀 수 있습니다.
전부 `js/config.js` 의 `EMBED_VIEW` 한 곳에 모아 두었습니다.

| 옵션 | 지금 값 | 무엇이 달라지나 |
| --- | --- | --- |
| `hotspotHints` | `true` (Figma 기본) | 빈 곳을 눌렀을 때 클릭 가능한 영역이 파랗게 반짝입니다. `false` 면 반응이 없어 화면이 멈춘 것처럼 느껴집니다 |
| `keyboardNav` | `false` | 화살표 키·스페이스로 다음 프레임 넘기기를 끕니다. 키보드로 작업을 건너뛰는 사고를 막습니다 |
| `hideUI` | `true` | Figma 툴바를 숨겨 앱처럼 보이게 합니다 |
| `scaling` | `scale-down-width` | 기기 영역 폭에 맞춰 축소합니다. `min-zoom` 은 원본 공유 링크와 같은 실제 크기지만 프레임이 더 크면 잘립니다 |

## 구성

```
ut/
  index.html
  assets/daangn-logo.svg   상단 로고
  data/responses.json      수집된 응답 (서버가 만듭니다 · 정적 공개 안 됨)
  css/
    seed-color.css       SEED 색 토큰 — Rootage color.json 에서 자동 생성
    seed-scale.css       SEED 간격 · radius · 타이포 · duration 토큰
    seed-components.css  SEED 컴포넌트 CSS 이식본 (ActionButton, SelectBox, TextInput …)
    ut.css               UT 화면 · 대시보드 레이아웃
  js/
    config.js     ← 프로토타입 주소 · 태스크 · 문항 · 옵션. 보통 여기만 고칩니다
    seed-icons.js SEED 아이콘 path (@karrotmarket/react-monochrome-icon 에서 추출)
    store.js      응답 저장 · 서버 전송 · CSV/JSON 내보내기
    charts.js     그룹 막대 / 비교 막대 / 변화량
    proto.js      Figma 임베드 제어 및 이벤트 수신
    survey.js     진행 엔진
    dashboard.js  응답 대시보드
    app.js        라우터
```

### 왜 seed-design 패키지를 직접 쓰지 않았나

`daangn/seed-design` 은 React / Vue / Lynx 구현체라 빌드 없는 정적 HTML 에서 import 할 수 없습니다.
그래서 seed-design 과 같은 source of truth 인 **Rootage 스펙에서 토큰과 컴포넌트 정의를 그대로 가져와**
CSS 로 옮겼습니다. 값은 임의로 바꾸지 않았고, 각 블록에 출처 스펙 경로를 주석으로 남겨 두었습니다.
아이콘도 실제 SEED 아이콘 패키지의 path 데이터를 씁니다.

## 대시보드 차트

지표의 성격에 따라 두 가지만 씁니다.

| 형태 | 쓰는 경우 | 지표 |
|---|---|---|
| **그룹 막대 (Small Multiples)** | 작업별로 값이 나올 때 | 태스크 성공률 · 평균 소요시간 · SEQ · 미스클릭 |
| **비교 막대** | 값이 하나뿐이라 차이만 보면 될 때 | 정보 탐색 용이성 · 선호 |

### 왜 꺾은선이 아니라 막대인가

작업 1 · 2 · 3 은 시간 순서가 아니라 **서로 다른 과제**입니다.
선으로 이으면 “작업이 진행될수록 좋아진다” 는 있지도 않은 추세가 읽히고,
개선 전/후 두 계열이 겹쳐 구분도 어려워집니다.

그래서 **지표 하나 = 카드 하나**로 나누고(Small Multiples), 카드 안에서 작업별로 칸을 갈라
개선 전/후 막대를 나란히 세웁니다. 볼 것이 “이 작업에서 얼마나 좋아졌나” 하나로 줄어듭니다.

- 한 쌍이 작업 하나입니다. 값은 **그 작업을 수행한 전체 참가자의 평균**이고, 참가자 한 명이 아닙니다.
  참가자가 2명이든 20명이든 막대 쌍의 개수는 작업 수만큼(기본 3개)입니다.
- 작업 이름은 축 아래에 그대로 적습니다 (`config.js` 의 `TASKS[].axisLabel`, 한글 8자 안쪽).
- 막대 위 라벨은 칸이 좁아 단위를 뺀 숫자만 적습니다. 단위는 카드 제목 아래에 한 번,
  마우스를 올리면 단위까지 함께 나옵니다.
- 응답이 없어 비교할 수 없는 칸(예: 개선 전에서 전원이 포기한 작업의 소요시간)은
  막대를 그리지 않고 `—` 와 `비교 불가` 로 둡니다. 0 으로 채우지 않습니다.

**개선 폭 배지** — 작업마다 축 아래에 붙습니다. 차이는 그 지표의 단위 그대로 적습니다.
비율(%)로 바꾸면 기준값이 작을 때 과장돼 보이기 때문입니다.
퍼센트 지표는 `%p` 로 적어 상대변화와 헷갈리지 않게 했습니다.
좋아졌으면 초록, 나빠졌으면 빨강입니다 — 방향은 지표마다 다릅니다
(성공률·SEQ 는 높을수록, 소요시간·미스클릭은 낮을수록 좋음).

**색** — 개선 전은 그레이, 개선 후는 당근 키컬러 주황 + 빗금입니다.
개선 전이 더 눈에 띄면 안 되기 때문에 기준선 역할만 하도록 채도를 뺐고,
개선 후는 색뿐 아니라 빗금 무늬로도 구분되므로 색만으로 계열을 읽지 않아도 됩니다.
빗금은 막대·범례가 같은 방향("/")·두께(1px)·간격(5px)을 쓰고, `ut.css` 의 `--hatch` 한 곳에서 관리합니다.
모든 막대에 값 라벨이 붙어 있고, 맨 아래 참가자별 표에서 같은 값을 숫자로 다시 볼 수 있습니다.

> 참고: 이 조합은 색각 검증 스크립트의 "카테고리 팔레트" 기준으로는 그레이가 채도·명도 항목에서
> 걸립니다. 두 계열이 대등한 카테고리가 아니라 **기준선 + 강조**라서 일부러 그렇게 둔 것이고,
> 두 색 사이 구분(ΔE 24~29)은 색각 이상 조건에서도 충분합니다.

**축** — 막대는 항상 0 에서 시작합니다. 눈금선은 점선으로 옅게 깔고, 소요시간처럼 값 범위가
회차마다 달라지는 지표는 실제 값에 맞춰 눈금을 다시 잡습니다(고정하면 막대가 뭉개집니다).

### 20블록으로 줄이면서 한 일

- 작업 직후 난이도(SEQ)를 별도 화면에서 **작업 카드 안으로** 옮겼습니다 (−6블록).
  기억이 가장 선명한 시점에 묻게 되어 측정에도 유리합니다.
- SUS 10문항을 화면 10개에서 **한 화면의 표**로 묶었습니다 (−10블록). 원래 SUS 는 한 장으로 받는 설문입니다.
- SUS 안내 화면은 표 위 설명으로 합쳤습니다 (−1블록).
- '당근에서 주로 무엇을 하시나요'(주 사용 목적)는 뺐습니다 (−1블록).
  참가자 세분화가 필요하면 `config.js` 의 participant 블록 뒤에 다시 넣으면 됩니다.

저장되는 항목과 키는 그대로입니다. 태스크 성공률 · 소요시간 · SEQ · 정보 탐색 용이성 ·
선호도 · 재방문 의향 · SUS 모두 전과 같이 집계됩니다.

### 지나온 문항으로 되돌아가기

왼쪽 목록에서 **이미 지나온 문항을 눌러 되돌아갈 수 있습니다.** 아직 가 보지 않은 문항은 잠겨 있습니다.
돌아가서 답을 고쳐도 앞서 기록한 작업 소요시간은 그대로 유지됩니다.

태스크는 PRD 08. 검증 계획 / Phase 02 의 핵심 Task 5개 중 3개가 켜져 있습니다.
`config.js` 의 `TASKS` 에서 `enabled: true` 로 바꾸면 나머지 2개도 들어갑니다.
태스크 하나가 늘 때마다 양쪽 구간에 1블록씩, 총 2블록이 추가됩니다(난이도는 작업 카드 안에 있습니다).

### 순서 효과

기본은 요청대로 **개선 전 → 개선 후** 고정입니다.
다만 나중에 본 화면이 유리해 보이는 순서 효과가 A/B 비교의 가장 큰 위협이라,
`OPTIONS.counterbalance = true` 로 두면 참가자마다 순서를 번갈아 제시하고 응답에 순서를 함께 기록합니다.
참가자가 6명 이상이면 켜는 쪽을 권합니다.

## 알아 둘 것

**자동으로 측정되는 것**

- 태스크별 소요시간 (페이지가 직접 재고, 프로토타입 로딩 시간은 빠집니다)
- 태스크 성공 / 포기 (참가자 자기보고)
- SEQ · 정보 찾기 쉬움 · 재방문 의향 · SUS · 선호도

**측정되지 않는 것**

- 탭 횟수 · 반응 없는 영역 탭(미스클릭) · 프로토타입 내 이동 경로

Figma 임베드가 `embed-host` 를 붙여도 `PRESENTED_NODE_CHANGED` / `MOUSE_PRESS_OR_RELEASE`
postMessage 를 보내지 않는 것을 확인했습니다(embed.figma.com · www.figma.com/embed 양쪽 모두).
수신 코드는 그대로 두었으니 Figma 쪽에서 이벤트가 열리면 자동으로 집계되기 시작하고,
그 전까지는 참가자 화면과 대시보드 모두 **"측정되지 않음"이라고 표시합니다**. 0 으로 위장하지 않습니다.

미스클릭이 꼭 필요하면 진행자가 화면 녹화로 세거나, Maze·Useberry 를 병행해야 합니다.

**그 밖에**

- 참가자가 Figma 쿠키 배너를 한 번 닫아야 할 수 있습니다. 세션 시작 전에 미리 한 번 열어 두면 깔끔합니다.
- 임베드 표시 배율은 `scaling=scale-down-width` 입니다. 원본 공유 링크의 `min-zoom`(실제 크기)은
  기기 영역보다 프레임이 커서 잘리고, `contain` 은 여백이 크게 남습니다. 디자인은 그대로이고 배율만 다릅니다.
- 테마는 light 고정입니다. 참가자 기기의 다크 모드가 설문 화면 색을 바꾸면 자극이 일정하지 않게 됩니다.
- 데스크톱(1280px 이상)에서 진행하는 것을 전제로 합니다. 좁아지면 좌측 레일이 숨고, 더 좁아지면 프로토타입이 위로 올라갑니다.
